```
     │        └─ StdQueue<T>  ──► System.Collections.Generic.Queue<T>
     ├─► Part1/PostfixEvaluator, InfixToPostfix ──► LinkedStack<T>
     ├─► Part3/*  (Josephus, BrowserHistory, RoundRobin, Huffman)
     ├─► Part4/*  (ListAlgorithms, BinaryTree)
     └─► Benchmarks/*  (генерация input.txt-подобных файлов + Timing)
```

Стек и обе «списочные» очереди — это **тонкие обёртки над одним и тем же `MyLinkedList<T>`**; отличаются только тем, с какого конца вставляют и удаляют:

| Структура | Вставка | Удаление |
|---|---|---|
| Стек | `AddFirst` (голова) | `RemoveFirst` (голова) |
| Очередь | `AddLast` (хвост) | `RemoveFirst` (голова) |

### 4.2 Конвейер обработки `input.txt`

```
input.txt ──read──► текст ──Split + parse──► Operation[] ──execute──► вывод (строки)
            └──────── «считывание» ────────┘ └─ «выполнение» ┘
```

* **Считывание** = `File.ReadAllText` + разбиение на токены + преобразование каждого токена в `Operation { Kind, Value, Raw }`.
* **Выполнение** = цикл по `Operation[]`, вызов методов структуры, передача результата в `Action<string> output`.
* В обычном запуске `output` = `Console.WriteLine`, в замерах `output` = пустая функция, чтобы **не измерять скорость консоли**.
* Эти два этапа измеряются раздельно, как требует задание («время на считывание и выполнение операций»).

### 4.3 Формат токена

| Токен | Операция (стек / очередь) |
|---|---|
| `1,значение` | `Push` / вставка в конец. Значение — число или слово; берётся всё после **первой** запятой |
| `2` | `Pop` / удаление |
| `3` | `Top` / просмотр начала |
| `4` | `isEmpty` |
| `5` | `Print` |
| что угодно другое, а также голое `1` | выводится сообщение об ошибке, выполнение **продолжается** |

Операции на пустой структуре не бросают исключение, а печатают понятное сообщение («стек пуст»).

## 5. Разбор алгоритмов

### 5.1 Свой связной список и стек

`MyLinkedList<T>` — односвязный список с указателями `Head`, `Tail` и счётчиком `Count`:

```
Head ─► [a|•]─►[b|•]─►[c|∅]   ◄─ Tail
```

Указатель `Tail` нужен, чтобы вставка в конец была за O(1), а не за O(n) (иначе очередь стала бы квадратичной).

**Стек.** Вершина стека — голова списка. `Push` создаёт узел, чья `Next` указывает на старую голову; `Pop` сдвигает голову на `Next`. Ни одна операция не проходит по списку, поэтому всё — O(1).

| Операция | Стек | Очередь (на списке) |
|---|---|---|
| Push / Enqueue | O(1) | O(1) |
| Pop / Dequeue | O(1) | O(1) |
| Top / Peek | O(1) | O(1) |
| isEmpty | O(1) | O(1) |
| Print | O(n) | O(n) |

Пример из задания `3 4 1,56 1,7 1,cat 2 5 4`:

```
Top(): стек пуст
isEmpty(): true
Push(56): элемент добавлен
Push(7): элемент добавлен
Push(cat): элемент добавлен
Pop(): удалён элемент cat
Print() (вершина слева): [7, 56]
isEmpty(): false
```

### 5.2 Очередь (часть 2)

Две реализации под одним интерфейсом `IMyQueue<T>`:

1. **`LinkedQueue<T>`** — на своём списке: `Enqueue` → `AddLast`, `Dequeue` → `RemoveFirst`. Каждый элемент — отдельный объект-узел в куче (≈ 32 байта: заголовок объекта + `Value` + `Next`).
2. **`StdQueue<T>`** — обёртка над `System.Collections.Generic.Queue<T>`, внутри — **кольцевой массив**: элементы лежат подряд, при переполнении массив удваивается (амортизированное O(1)).

Обе дают идентичный вывод — это проверяется дифференциальным тестом на 5000 случайных операций (`selftest`).

### 5.3 Вычисление постфиксной записи

**Идея.** В постфиксной записи операция стоит *после* операндов, поэтому скобки и приоритеты не нужны: достаточно одного прохода слева направо и стека значений.

**Алгоритм:**

```
для каждого токена t слева направо:
    если t — число:               Push(t)
    иначе если t — бинарная ‹op›: b ← Pop();  a ← Pop();  Push(a ‹op› b)
    иначе если t — унарная ‹f›:   a ← Pop();  Push(f(a))
    иначе:                        ошибка «неизвестный токен»
в конце: в стеке должно быть ровно одно значение — это результат
```

Важный нюанс: **правый операнд снимается первым** (`b`, затем `a`), иначе `-`, `:` и `^` дадут неверный результат.

**Разбор примера с рисунка** `7 8 + 3 2 + /` (в точности как на рисунке, стек показан от основания к вершине):

| Токен | Действие | Стек |
|---|---|---|
| `7` | Push | `[7]` |
| `8` | Push | `[7, 8]` |
| `+` | Pop 8, Pop 7 → Push 15 | `[15]` |
| `3` | Push | `[15, 3]` |
| `2` | Push | `[15, 3, 2]` |
| `+` | Pop 2, Pop 3 → Push 5 | `[15, 5]` |
| `/` | Pop 5, Pop 15 → Push 15/5 | `[3]` |

Результат: **3**. Программа печатает такую трассу для каждого выражения из `postfix.txt`.

**Поддерживаемые операции**

| Токен | Арность | Примечание |
|---|---|---|
| `+` `-` `*` | 2 | |
| `:` и `/` | 2 | деление; деление на 0 → ошибка |
| `^` | 2 | возведение в степень (`Math.Pow`) |
| `ln` | 1 | только для x > 0 |
| `sqrt` | 1 | только для x ≥ 0 |
| `sin` `cos` | 1 | аргумент в **радианах** |
| `~` | 1 | унарный минус (см. [допущения](#9-допущения-и-ограничения)) |

Дополнительно: отрицательные литералы (`-5`), дробные числа через точку (`2.5`), экспоненциальная запись (`1e3`), любой регистр у имён функций. Результат операции проверяется на `NaN`/`∞`, ошибки выдаются как `ExpressionException` с понятным текстом: нехватка операндов, лишние операнды, неизвестный токен, область определения.

**Корректность (инвариант).** После обработки *i*-го токена в стеке лежат значения всех «ещё не использованных» подвыражений, найденных в первых *i* токенах, причём в порядке их появления. Бинарная операция всегда берёт два верхних элемента — это два последних завершённых подвыражения, то есть именно её операнды.

**Оценка сложности.**

Пусть выражение содержит *n* токенов: *k* чисел и *m* операций (*n = k + m*; для корректного выражения из одних бинарных операций *m = k − 1*).

* Каждый токен обрабатывается **один раз**. Для числа — 1 `Push`; для бинарной операции — 2 `Pop` + 1 `Push`; для унарной — 1 `Pop` + 1 `Push`. Все операции стека — O(1). Значит, на токен приходится не более 3 операций стека и 1 арифметическое действие: **T(n) ≤ c·n = Θ(n)**.
* Разбор токена (`double.TryParse`) стоит O(длина токена); при ограниченной длине чисел это O(1), в общем случае сумма длин токенов = O(длина строки).
* **Память:** глубина стека ≤ *k*. Худший случай — все числа идут подряд, а потом операции (`1 1 1 … 1 + + … +`): стек разрастается до *k* ≈ *n*/2 элементов. Итого **O(n)** памяти (по 1 узлу на значение). Лучший случай — O(1) (`1 1 + 1 + 1 + …`).
* Нижняя граница: каждый токен нужно прочитать хотя бы раз, поэтому Ω(n) — алгоритм **асимптотически оптимален**.

**Эмпирическая проверка** (худший случай по памяти; время = разбор + вычисление; режим `bench-postfix`):

| Токенов | Время (разбор + вычисление), мс | нс на токен |
|---:|---:|---:|
| 19,999 | 1.72 | 85.77 |
| 99,999 | 9.34 | 93.44 |
| 199,999 | 16.98 | 84.90 |
| 999,999 | 91.96 | 91.96 |
| 1,999,999 | 288.22 | 144.11 |

Время на один токен держится на уровне ≈ 85–95 нс при росте *n* в 50 раз — линейность подтверждена. Скачок до ≈ 144 нс на 2 млн токенов — это давление на кэш и сборщик мусора (два миллиона строк токенов + миллион узлов стека), а не рост асимптотики.

### 5.4 Перевод инфиксной записи в постфиксную

Используется **алгоритм сортировочной станции** (shunting-yard, Э. Дейкстра). Числа сразу уходят в выходную строку, а операции ждут в стеке операций, пока не придёт операция с меньшим приоритетом (тогда ожидающие выталкиваются в вывод).

**Приоритеты и ассоциативность**

| Приоритет | Операции | Ассоциативность |
|---|---|---|
| 1 | `+` `-` | левая |
| 2 | `*` `:` `/` | левая |
| 3 | унарный минус (`~`) | правая (префиксный) |
| 4 | `^` | **правая** (`2^3^2 = 2^(3^2) = 512`) |
| 5 | функции `ln cos sin sqrt` | — |

**Правила обработки токенов**

* **Число** → в вывод.
* **Функция** → в стек (после неё обязательно `(`).
* **`(`** → в стек.
* **`)`** → выталкивать операции в вывод до `(`; саму `(` выбросить; если под ней функция — вытолкнуть и её.
* **Бинарная операция `op`** → пока на вершине операция с большим приоритетом (или равным, если `op` левоассоциативна) — выталкивать в вывод; затем `op` в стек.
* **Унарный минус** распознаётся по контексту: `-` в начале, после `(` или после другого оператора. В стек кладётся `~` без выталкивания (префиксный оператор). Унарный плюс игнорируется.
* В конце — вытолкнуть всё оставшееся (встреча `(` означает несбалансированные скобки).

Для различения «операнд ожидается / операция ожидается» используется флаг `expectOperand`; он же ловит ошибки вида `2+*3`, `2 3`, `2+`, `2(3)`.

**Трассировка `3+4*2/(1-5)^2`** (программа печатает такую таблицу; стек операций — вершина слева):

| Токен | Стек операций | Вывод |
|---|---|---|
| `3` | `[]` | `3` |
| `+` | `[+]` | `3` |
| `4` | `[+]` | `3 4` |
| `*` | `[*, +]` | `3 4` |
| `2` | `[*, +]` | `3 4 2` |
| `/` | `[/, +]` | `3 4 2 *` |
| `(` | `[(, /, +]` | `3 4 2 *` |
| `1` | `[(, /, +]` | `3 4 2 * 1` |
| `-` | `[-, (, /, +]` | `3 4 2 * 1` |
| `5` | `[-, (, /, +]` | `3 4 2 * 1 5` |
| `)` | `[/, +]` | `3 4 2 * 1 5 -` |
| `^` | `[^, /, +]` | `3 4 2 * 1 5 -` |
| `2` | `[^, /, +]` | `3 4 2 * 1 5 - 2` |
| *конец* | `[]` | `3 4 2 * 1 5 - 2 ^ / +` |

Результат вычисления: `3 + 8/16 = 3.5`.

**Сложность.** Каждый токен кладётся в стек операций не более одного раза и снимается не более одного раза, поэтому **O(n) по времени и O(n) по памяти**.

Режим `infix` дополнительно подставляет полученную постфиксную запись в `PostfixEvaluator` и печатает значение — так связка проверяется «в замкнутом цикле».

### 5.5 Часть 3 — применение динамических структур

| Структура | Пример применения | Класс | Как устроено | Сложность |
|---|---|---|---|---|
| **Список** | Задача Иосифа Флавия | `Josephus` | Круговой односвязный список: узел `prev` стоит перед «текущим»; k−1 шагов вперёд, затем `prev.Next = victim.Next` исключает узел за O(1). Проверка по рекуррентной формуле `J(m) = (J(m−1)+k) mod m` | O(N·k) времени, O(N) памяти |
| **Стек** | «Назад» / «Вперёд» в браузере | `BrowserHistory` | Два стека: назад и вперёд. `Visit` кладёт текущую страницу в «назад» и **очищает** «вперёд»; `Back`/`Forward` переносят страницу между стеками | O(1) на команду |
| **Очередь** | Планировщик процессов Round-Robin | `RoundRobinScheduler` | Очередь готовых процессов: берём процесс, даём ему квант; не завершился — в хвост очереди. Строится диаграмма Ганта, считаются время завершения, оборота и ожидания | O(S) операций, S = Σ⌈burstᵢ / q⌉ |
| **Дерево** | Кодирование Хаффмана | `Huffman` | Приоритетная очередь деревьев по частоте; два самых редких сливаются в родителя, пока не останется одно дерево. Код символа — путь от корня (влево `0`, вправо `1`). Коды префиксные, декодирование — спуск по дереву | O(m log m) построение (m — число разных символов) |

Для `abracadabra` Хаффман даёт 23 бита против 88 при кодировании по 8 бит на символ (сжатие в 3,83 раза).

> **Про уникальность.** По условию пример должен быть уникальным в группе. Выбраны менее «ходовые», чем LRU-кэш, скобочные последовательности или обход графа в ширину, примеры — но согласуйте выбор с группой. Запасные варианты: список — сложение многочленов, музыкальный плейлист; стек — отмена/повтор действий в редакторе, DFS в лабиринте; очередь — обход графа в ширину, буфер печати; дерево — дерево выражения, префиксное дерево (trie).

### 5.6 Часть 4 — алгоритмы над собственным списком

Все функции меняют ссылки узлов **на месте** (копия списка не создаётся) и поддерживают согласованность `Head`, `Tail`, `Count`. После каждой функции демонстрация проверяет эту согласованность автоматически (`[Head/Tail/Count: OK]`).

**1. Переворот (`Reverse`)** — O(n) времени, O(1) памяти.
Три указателя `prev`, `cur`, `next`; у каждого узла ссылка разворачивается назад:

```
до:    1 → 2 → 3 → ∅
шаг 1: ∅ ← 1   2 → 3
шаг 2: ∅ ← 1 ← 2   3
шаг 3: ∅ ← 1 ← 2 ← 3      Head = 3, Tail = 1
```

**2. Перенос крайних элементов**

* `MoveLastToFront` — ищется предпоследний узел (O(n)), последний отцепляется и подцепляется перед головой.
* `MoveFirstToBack` — **O(1)** благодаря указателю `Tail`: голова сдвигается на `Next`, бывший первый узел прицепляется после хвоста.
* Для пустого списка — исключение (функции определены для **непустого** списка); для списка из одного элемента — ничего не меняется.

**3. Количество различных (`CountDistinct`)** — один проход, добавление значений в `HashSet<int>`; ответ — размер множества. O(n) в среднем, O(k) памяти. (Без дополнительной памяти можно за O(n²) вложенными проходами.)

**4. Удаление неуникальных (`RemoveNonUnique`)** — два прохода:
сначала подсчёт частот в `Dictionary<int,int>`, затем проход с `prev`/`cur`, выбрасывающий узлы, чья частота больше 1. Остаются только значения, встречавшиеся **ровно один раз**. Для `5 3 8 3 1 5 9 3 7` результат — `8 1 9 7`.
Вариант толкования — оставить по одному первому вхождению — реализован отдельно как `RemoveDuplicatesKeepFirst` (результат `5 3 8 1 9 7`). См. [допущения](#9-допущения-и-ограничения).

**Дерево с рисунка** (`BinaryTree`)

Строка `ABD*G***CE**FH**J**` — это **прямой обход** (корень → левое → правое), где `*` обозначает пустую ссылку (`NULL`). Разбор рекурсивный:

```
Build():
    c ← следующий символ
    если c = '*':  вернуть NULL
    узел ← новый(c)
    узел.Left  ← Build()
    узел.Right ← Build()
    вернуть узел
```

Разбор строки рисунка: `A` → левое `B` → левое `D` → левое `*`, правое `G` → `**` (оба пусты); вернулись в `B`: правое `*`; вернулись в `A`: правое `C` → левое `E` (`**`), правое `F` → `H` (`**`), `J` (`**`). Получается ровно то дерево, что на рисунке:

```
        A
      /   \
     B     C
    /     / \
   D     E   F
    \       / \
     G     H   J
```

Строка проверяется на корректность: нехватка символов (`AB*`) или лишние символы после дерева (`A**B`) дают `FormatException`.

Программа выводит: таблицу узлов в стиле рисунка (левая/правая ссылки, `NULL`), дерево, повёрнутое на 90°, четыре обхода, характеристики и обратную сериализацию (она обязана совпасть с исходной строкой):

| Обход | Результат |
|---|---|
| Прямой (корень-лево-право) | `ABDGCEFHJ` |
| Симметричный (лево-корень-право) | `DGBAECHFJ` |
| Обратный (лево-право-корень) | `GDBEHJFCA` |
| По уровням (в ширину, на очереди) | `ABCDEFGHJ` |

Узлов — 9, листьев — 4, высота — 4. Построение и обходы — O(n); глубина рекурсии равна высоте дерева.

## 6. Чем алгоритмы отличаются от альтернатив

### 6.1 Стек на связном списке и другие реализации стека

| | Свой список (эта работа) | Массив с индексом вершины | `Stack<T>` из BCL |
|---|---|---|---|
| Push | O(1) **всегда**, выделение узла | амортизированное O(1), иногда O(n) при перевыделении | амортизированное O(1) |
| Память на элемент | значение + ссылка + заголовок объекта | только значение | только значение |
| Локальность в кэше | плохая (узлы разбросаны) | отличная | отличная |
| Предел размера | только память | перевыделение | то же |
| Когда лучше | нужны гарантированные O(1), стек живёт недолго, цель — учебная | почти всегда в производственном коде | почти всегда |

Из замеров: `Push` 200 000 элементов — ≈ 6 мс. Для сравнения: в части 2 массивная реализация (`Queue<T>`) быстрее списочной в 1,4–2,1 раза, и для стека на массиве ожидается сопоставимый выигрыш (для стека такое сравнение отдельно не замерялось).

### 6.2 Постфиксные вычисления и другие способы вычислять выражения

| Подход | Особенности | Отличие от нашего |
|---|---|---|
| **Постфиксная запись + стек** (здесь) | один проход, O(n), нет скобок и приоритетов, нет рекурсии | — |
| Прямое вычисление инфиксной строки рекурсивным спуском | сразу даёт число, но грамматика и приоритеты зашиты в код; рекурсия | нет промежуточной записи, сложнее расширять (каждая новая операция — правка грамматики) |
| Построение дерева выражения и его обход | наглядно, позволяет оптимизировать и упрощать | дополнительная память под узлы, два прохода |
| Префиксная запись (польская) | операция перед операндами | читать нужно справа налево; идея та же |
| `eval` / компиляция выражения | быстро, но небезопасно и зависит от платформы | наш вариант изолирован и предсказуем |

### 6.3 Сортировочная станция Дейкстры и другие конвертеры

| Подход | Отличие |
|---|---|
| **Shunting-yard** (здесь) | один проход, O(n), приоритеты — в таблице (расширяется одной строкой), нет рекурсии, лёгкая трассировка |
| Рекурсивный спуск, генерирующий постфикс | тоже O(n), но грамматика зашита в функции; глубина рекурсии растёт с вложенностью скобок |
| Полная расстановка скобок + обход дерева | двухпроходный, дополнительная память |
| Наивный поиск «главной» операции с рекурсивным разбиением | O(n²) в худшем случае |

### 6.4 Очередь на списке и на кольцевом массиве

Очередь на списке — O(1) на любую операцию, но с выделением узла на каждый `Enqueue`. `Queue<T>` — амортизированное O(1) без выделения на каждый элемент и с хорошей локальностью. Как следствие, на практике `Queue<T>` быстрее в 1,4–2,1 раза почти во всех сценариях (раздел 7).

### 6.5 Алгоритмы списков (часть 4)

| Задача | Наш способ | Альтернатива и отличие |
|---|---|---|
| Переворот | перешивание ссылок, O(1) памяти | через стек / новый список — O(n) дополнительной памяти; рекурсивный переворот — риск переполнения стека вызовов |
| Последний → в начало | поиск предпоследнего, перешивание | на двусвязном списке — O(1), но нужен второй указатель в каждом узле |
| Различные элементы | `HashSet`, O(n) | сортировка копии — O(n log n); вложенные циклы — O(n²) без доп. памяти |
| Неуникальные | подсчёт частот + один проход удаления, O(n) | вложенные циклы с удалением — O(n²) |

### 6.6 Часть 3

| Пример | Наш способ | Альтернатива |
|---|---|---|
| Иосиф Флавий | круговой список, O(N·k) | рекуррентная формула — O(N) (используется как проверка, но она не даёт порядок выбывания); дерево порядковых статистик — O(N log N) для больших k |
| Кодирование Хаффмана | жадное построение бинарного дерева, оптимальные префиксные коды | Шеннона–Фано — не всегда оптимален; RLE — выигрывает только на длинных повторах; арифметическое кодирование — лучше сжимает, но сложнее |
| Round-Robin | очередь, справедливое распределение квантов | FCFS — проще, но «длинные» процессы блокируют остальных; SJF — меньше среднее ожидание, но возможен голод |
| История браузера | два стека, O(1) | один массив с указателем «текущей» позиции — эквивалентно по сложности |

## 7. Результаты замеров времени

**Методика.** Режимы `bench-stack` и `bench-queue` генерируют файлы в формате `input.txt` (случайные значения «число или слово», `Random(42)` — наборы воспроизводимы), затем для каждого набора:

1. отдельно измеряется **считывание** (`ReadAllText` + разбор в `Operation[]`) и **выполнение** операций;
2. вывод результатов отбрасывается (измеряется структура, а не консоль);
3. перед каждым запуском — сборка мусора (вне замера), берётся **медиана** из 5 запусков (из 3 для наборов ≥ 500 000 операций);
4. сборка Release, окружение: Ubuntu 24.04, .NET 8.0.134, 1 vCPU. Абсолютные значения на вашем компьютере будут другими, соотношения — близкими.

| Случайная смесь, 10,000 оп. | 10,000 | 36 | 0.81 | 0.37 | 1.18 |
| Случайная смесь, 100,000 оп. | 100,000 | 367 | 8.61 | 5.39 | 13.99 |
| Случайная смесь, 1,000,000 оп. | 1,000,000 | 3,669 | 110.74 | 333.67 | 444.41 |

Выводы:

* **Размер.** Время растёт линейно: 10 000 → 100 000 операций (×10) даёт ×11,9 по итогу. На 1 000 000 операций «случайной смеси» время выполнения вырастает непропорционально (333 мс): в смеси есть редкие `Print` (≈ 100 штук), каждая из которых обходит стек глубиной в десятки тысяч элементов — O(n) на `Print`.
* **Состав.** При одинаковой длине 200 000 операций итоговое время различается в **36 раз** (11,9 мс у «Только Pop на пустом стеке» против 431,7 мс у «Push + Print каждые 2000»), а время одного лишь выполнения — более чем в 600 раз (0,63 против 416 мс). Причина: все операции стека O(1), кроме `Print`, который O(n) и ещё строит строку. «Pop на пустом стеке» сводится к проверке `head == null` и выводу сообщения. Итог: на стоимость набора влияет **не число операций, а число и «глубина» вызовов `Print`**.
* **Считывание** линейно по числу токенов: ≈ 55–110 нс на токен (разбиение строки + разбор). Для наборов **без** `Print` считывание **дороже** выполнения в 2,5–18 раз: разбор строк стоит заметно больше, чем O(1)-операции со стеком.

Выводы:

* **Разная длина:** обе реализации масштабируются линейно, `Queue<T>` стабильно быстрее в 1,1–2,1×.
* **Одинаковая длина, разный состав:** наибольшее **относительное** расхождение — набор «Только Dequeue (пустая структура)» (**3,6×**, 1,80 против 0,50 мс). Но в абсолютных цифрах оно мало (1,3 мс), поэтому подвержено шуму измерений (вероятно, играют роль и вызов через интерфейс, и формирование сообщения); поэтому наиболее показательное **абсолютное** расхождение — «Enqueue + Print каждые 2000 оп.» (**414 против 274 мс**, +139 мс, 1,5×): вероятная причина — обход цепочки узлов, разбросанных по куче, у списка против обхода подряд лежащего массива у `Queue<T>` (лучше использует кэш процессора). Эта причина — предположение: профилировщиком она не проверялась.
* Для вставки: `Enqueue` в список требует выделения узла (`new`) для каждого элемента, а в `Queue<T>` — запись в массив; это даёт стабильный выигрыш ≈ 1,5× у `Queue<T>` на наборах с вставками.
* Самые близкие результаты на коротких наборах (до 1000 операций) — разницу скрывает шум измерений.

Файлы замеров (`bench/*.txt` и `benchmark_stack.md`, `benchmark_queue.md`, `benchmark_postfix.md`) создаются в **текущей папке**.

### 8.4 Форматы входных файлов

Файлы ищутся в таком порядке: путь, как указан → `./data/` → `data/` рядом с исполняемым файлом.

| Файл | Формат | Пример |
|---|---|---|
| `input.txt` | токены через пробел: `1,значение`, `2`, `3`, `4`, `5` | `3 4 1,56 1,7 1,cat 2 5 4` |
| `postfix.txt` | одно выражение в строке, токены через пробел; `#` — комментарий | `7 8 + 3 2 + /` |
| `infix.txt` | одно выражение в строке; пробелы необязательны | `3+4*2/(1-5)^2` |
| `list.txt` | целые числа через пробел, запятую или перевод строки | `5 3 8 3 1 5 9 3 7` |
| `processes.txt` | 1-я строка: `quantum N`; далее `Имя ВремяВыполнения` | `P1 5` |
| `tree.txt` | строка прямого обхода, `*` = NULL | `ABD*G***CE**FH**J**` |

### 8.5 Как читать вывод

* **Стек и очередь:** `Print()` показывает вершину стека / начало очереди **слева**.
* **Постфикс:** после каждого токена печатается стек от основания к вершине.
* **Инфикс:** после каждого токена — стек операций (вершина слева) и текущий вывод.
* **Ошибки** выводятся красным: `Ошибка: …`; в файле с несколькими выражениями обработка продолжается со следующей строки.
* **Коды возврата** (в командном режиме): `0` — успех, `1` — ошибка данных/файла, `2` — неизвестная команда; для `selftest` — `1`, если есть упавшие проверки.

### 8.6 Как воспроизвести замеры для отчёта

1. Соберите Release (`dotnet build -c Release`).
2. Закройте тяжёлые программы, подключите ноутбук к питанию.
3. Запустите `bench-stack`, `bench-queue`, `bench-postfix`.
4. Перенесите таблицы из `benchmark_*.md` в отчёт. Для повторяемости наборы детерминированы (`Random(42)`).
5. Для собственных наборов создайте файл формата `input.txt` и запустите `stack файл` или `queue файл` — вывод будет на экране.

## 9. Допущения и ограничения

1. **Символ «)» в списке операций постфиксной записи.** В тексте задания перечень операций заканчивается знаком `«)»`, что выглядит как искажённый символ. Он трактуется как **унарный минус**, который в постфиксной записи обозначается `~` (`5 ~` = −5). В инфиксной записи унарный минус пишется как обычный `-` (`-2^2`, `2*-3`, `-(1+2)`) и конвертируется в `~` автоматически. Если вы имели в виду другую операцию — её легко добавить в `IsUnary`/`ApplyUnary` и таблицу приоритетов.
2. **Деление** допускается и как `:` (по тексту задания), и как `/` (как в примере задания `7 8 + 3 2 + /`).
3. **Неуникальные элементы (п. 4 части 4).** Выбрано буквальное прочтение: удаляются *все* вхождения значений, встречающихся более одного раза. Прочтение «оставить по одному вхождению» реализовано как `RemoveDuplicatesKeepFirst`.
4. **Тригонометрия** — в радианах; числа — `double`, десятичный разделитель — точка (культура `Invariant`, поэтому результат не зависит от региональных настроек ОС).
5. **Рекурсия в дереве.** Построение, обходы и высота дерева рекурсивны; для вырожденного дерева из десятков тысяч узлов возможно переполнение стека вызовов. Для дерева с рисунка и учебных данных это неважно.
6. **Круговой список** в `Josephus` — отдельный внутренний класс; в остальных частях используется `MyLinkedList<T>`.
7. **Примеры части 3** нужно согласовать с группой на уникальность (см. раздел 5.5).
8. **Замеры** зависят от машины, фоновой нагрузки и состояния кэша ОС; файл при первом чтении может читаться с диска. Поэтому используется медиана, а в отчёт нужно переносить результаты, снятые именно на вашем компьютере.
